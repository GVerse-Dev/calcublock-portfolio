# 알려진 한계와 개선 계획

포트폴리오 목적의 저장소이므로 **현재 코드의 문제를 그대로 적습니다.**
아래는 전부 스스로 진단한 항목이고, 수치는 원본 저장소 기준 실측값입니다.

> 이 프로젝트를 하면서 "이 구조가 왜 이렇게 됐는지, 지금 어디가 문제인지"를 적어 두는 게
> 나중에 가장 도움이 됐습니다. 그래서 개선 계획과 함께 남겨 둡니다.

---

## 1. Manager 싱글톤 결합도 — 최우선

**증상.** 자체 코드 전체에 `.Instance` 호출이 **179군데** 분포합니다.

| 파일 | 호출 수 |
|---|---|
| `IGGameController.cs` | 32 |
| `MainPanel.cs` | 19 |
| `PauseView.cs` | 14 |
| `GameOverPopup.cs` | 13 |
| `HUDView.cs` | 9 |

**문제.**

1. **의존성이 코드 안에 숨습니다.** 클래스 시그니처만 봐서는 무엇에 의존하는지 알 수
   없습니다. `IGGameController`가 무엇을 필요로 하는지 알려면 681줄을 다 읽어야 합니다.
2. **단위 테스트에서 대체가 불가능합니다.** `.Instance`는 정적 접근이라 가짜 객체를 끼워넣을
   자리가 없습니다.
3. **초기화 순서 의존이 암묵적입니다.** `IGEngine`이 순서대로 부르지만, 그 순서가 왜 그런지는
   코드에 없습니다.

**증거.** 이 부채가 실제로 무엇을 막고 있는지는 테스트 분포로 드러납니다.
EditMode 테스트 79개가 전부 `ExpressionEvaluator` — **정적 클래스이고 의존성이 없는 유일한
핵심 로직** — 에 몰려 있습니다. 다른 걸 테스트하고 싶어도 씬을 띄워야 합니다
(`PlayModeTestBase`가 존재하는 이유입니다).

**개선 방향.** 초기화 시점 주입으로 전환합니다. 전면 교체가 아니라 단계적으로 갑니다.

```
1단계  IGGameController 부터 의존성을 초기화 파라미터로 노출
2단계  그 상태로 EditMode 테스트를 붙일 수 있는지 확인 (실효성 검증)
3단계  효과가 확인되면 Controller → View 순으로 확대
```

전면 리팩터링을 먼저 하지 않는 이유는, 주입으로 바꿔도 테스트가 못 붙는 지점이 있을 수 있고
그걸 모른 채 179군데를 다 고치면 되돌리기 어렵기 때문입니다.

## 2. GameStateManager는 상태 머신이 아니라 상태 보관함입니다

**증상.** `GameState` enum과 `OnGameStateChanged` 이벤트는 있으나 **전이 유효성 검사가
없습니다.**

```csharp
public void SetGameState(GameState newState) {
    if (CurrentState == newState) return;   // 중복 호출만 차단
    CurrentState = newState;                // 어떤 상태 → 어떤 상태든 허용
    ...
}
```

**문제.** `GameOver → Playing` 직행처럼 성립하면 안 되는 전이가 **코드 수준에서 막혀 있지
않습니다.** 지금은 호출부에서 순서를 지켜 주는 것에만 의존하고 있어서, 시간이 지나면 놓칠 여지가
있습니다.

이름이 `Manager`라서 상태 머신처럼 보이지만 실제로는 **값 하나와 이벤트 하나**입니다.
이름이 하는 일보다 커서, 읽는 사람이 오해하기 쉽습니다.

**개선 방향.** 허용 전이 테이블을 정의하고 위반 시 차단·경고합니다.
**전이 규칙 자체를 테스트 대상으로 승격**합니다 — 이건 싱글톤 부채와 무관하게 지금 당장
할 수 있는 몇 안 되는 개선입니다.

## 3. Controller 비대화

| 파일 | LOC |
|---|---|
| `IGGameController.cs` | 681 |
| `IGBlockController.cs` | 539 |
| `IGBoardController.cs` | 495 |

**문제.** 입력 해석, 상태 갱신, 뷰 갱신, 매니저 호출이 한 클래스에 함께 있습니다.
`IGGameController`에 `.Instance` 호출이 32번 있는 것도 이것의 다른 얼굴입니다 —
**하는 일이 많으니 아는 것도 많습니다.**

**개선 방향.** 단일 책임 기준으로 분리합니다.
**책임 분리를 먼저** 하려고 합니다. 나머지는 책임이 갈린 뒤에 손대는 게 순서라고 생각합니다.

> 이 항목은 1번과 함께 풀어야 합니다. 의존성이 숨어 있는 상태로 클래스만 쪼개면
> 결합만 늘어납니다.

## 4. 환경 설정값 하드코딩

**증상.** 광고 단위 ID 등 환경 의존 값이 소스에 상수로 박혀 있습니다
([`AdUnitIds.cs`](../Assets/Scripts/Ads/AdUnitIds.cs)).

**실제로 비용을 치른 사례.** [세이브 무결성](save-integrity.md) 문서에 나오는
`RECOVERY_GAMES_PLAYED = 4`는 `AdGatePolicy.GracePeriodGames = 3`보다 커야 한다는
제약이 있는데, 후자가 `private`이라 참조할 수 없어 **손으로 맞추고 주석에 경고를
달았습니다.**

```csharp
// AdGatePolicy.GracePeriodGames(현재 3)는 private이라 참조할 수 없어,
// 어떤 튜닝값이든 확실히 넘도록 넉넉히 잡는다.
// 튜닝값이 바뀌면 여기도 함께 올릴 것.
```

주석으로만 묶어 둔 제약이라 한쪽만 고치면 조용히 어긋납니다. 설정값이 코드 여기저기에
흩어져 있어서 생긴 비용입니다.

**개선 방향.** ScriptableObject 기반 환경 설정으로 분리하고 빌드 시 주입합니다.
그러면 관련 값들이 한 자리에 모여 서로의 제약을 표현할 수 있습니다.

## 5. CI 없음

**증상.** 빌드 자동화는 로컬까지만 되어 있습니다 — Unity 에디터 메뉴(`Window → Build`)와
배치모드 스크립트입니다. **원격 CI는 붙이지 않았습니다.**

**이유.** Unity 빌드는 러너 디스크 용량 문제로 실패가 잦아 유지에 손이 많이 갑니다.
1인 프로젝트에서 우선순위를 뒤로 뒀습니다.

**그래도 로컬에서 지킨 것.** 스토어 빌드는 릴리스 keystore와 alias 비밀번호가 채워져 있지
않으면 **빌드를 실패시킵니다**([`BuildScript.cs`](../Assets/Editor/BuildScript.cs)).
디버그 키로 서명된 AAB가 스토어로 올라가는 사고를 코드 수준에서 막습니다.
CI가 없는 상황에서 **가장 비싼 실수 하나만이라도 자동으로 막자**는 판단이었습니다.

> 이 저장소의 이전 README에는 저장소에 없는 GitHub Actions 워크플로 파일로 걸린 링크가
> 있었습니다. 확인해 보고 지웠습니다.

## 6. 시뮬레이션 규칙의 이중 관리

**증상.** [시뮬레이션 레이어](automated-qa.md)가 게임 규칙을 별도로 재현합니다.
프로덕션 규칙이 바뀌면 양쪽을 함께 고쳐야 합니다.

**완화한 부분.** 타일 확률 생성(`TileValueGenerator`, `TilePhaseProfile`)과
점수 계산(`ExpressionEvaluator`)은 **프로덕션 코드를 그대로 가져다 씁니다.**
위험의 가장 큰 부분은 덮었습니다.

**남은 부분.** 배치 판정과 클리어 판정은 여전히 중복입니다.
시뮬레이션이 조용히 실제 게임과 달라지면, 나오는 CSV는 **틀린 근거**가 됩니다.

**개선 방향.** 보드 판정 로직을 렌더링 비의존 순수 클래스로 추출해 양쪽이 공유하게 합니다.
`BoardGrid`가 그 방향의 시작점입니다.

## 7. `ExpressionEvaluator` 파이프라인 이중화

`Evaluate`와 `EvaluateWithTracking`이 사실상 같은 파이프라인을 두 벌 갖고 있습니다
(후자는 각 토큰이 원본 타일 인덱스를 추적합니다).

정규화 규칙을 바꾸면 양쪽을 함께 고쳐야 합니다. 지금은 규칙이 안정적(4단계)이라 감수하고
있습니다.

**개선 방향.** 규칙이 더 늘면 인덱스 추적 버전으로 일원화하고, 일반 버전은 그 위의 얇은
래퍼로 만듭니다.

## 8. 구독 해제 규율에 강제 장치가 없습니다

UniRx 구독은 `AddTo(gameObject)`로 정리하는 것이 프로젝트 규칙이지만 **강제 장치가
없습니다.** 정적 이벤트(`ScreenChangeWatcher.OnChanged` 등)는 `AddTo`도 못 쓰고 수동으로
해제해야 합니다.

실제로 **구독 누수가 게임오버 소프트락을 만든 적이 있습니다.** 파괴된 `MonoBehaviour`가
이벤트를 받아 코루틴을 시작하려다 실패하는 형태였습니다.

**현재 대응.** [AutoPlayBot](automated-qa.md)이 장시간 플레이로 이런 누적을 탐지합니다.
사후 탐지이지 사전 방지가 아닙니다.

**개선 방향.** 구독 지점을 `UIBaseView` 같은 공통 베이스로 모아 해제를 기반 클래스가
책임지게 합니다.

## 우선순위

```
지금 할 수 있는 것 (부채와 무관)
  #2 상태 전이 테이블  ← 가장 비용 대비 효과가 크다
  #5 (현 상태 유지, 명시만)

1번을 풀어야 열리는 것
  #3 Controller 분리
  테스트 커버리지 확대 전반

여유가 생기면
  #6 보드 판정 공유       #7 파이프라인 일원화
  #4 설정 외부화          #8 구독 관리 베이스
```

**#1이 병목이고, 나머지 절반이 거기 묶여 있습니다.** 그래서 전면 리팩터링이 아니라
`IGGameController` 한 곳에서 실효성을 검증하는 단계적 접근을 택했습니다.
