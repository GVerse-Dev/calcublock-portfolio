# 세이브 무결성 — 위협 모델부터 되감기 방어까지

> 📄 [`SessionIntegrity.cs`](../Assets/Scripts/Storage/SessionIntegrity.cs) ·
> [`SaveManager.cs`](../Assets/Scripts/Managers/SaveManager.cs) ·
> [`AdGatePolicy.cs`](../Assets/Scripts/Ads/AdGatePolicy.cs)

무엇을 막으려는지 정하고 → 실기기로 공격 가능성을 확인하고 → 방어를 설계하고 →
그 방어가 못 막는 것까지 적어 둔 과정의 기록입니다.

## 1. 위협 모델을 실기기로 확인했습니다

세이브는 `Application.persistentDataPath`에 있습니다. Android에서 이 경로는
**외부 앱전용 저장소**입니다.

```
/storage/emulated/0/Android/data/<package>/files/gameData.json
```

**USB 디버깅만 켜면 루팅 없이 `adb pull` / `adb push`로 통째 교체할 수 있습니다.**
그리고 **릴리스 빌드에서도 그렇다는 것을 실기기로 확인했습니다** — non-debuggable이라
`run-as`는 거부되지만 이 경로는 열려 있습니다.

> 이 확인이 중요한 이유는, `run-as`가 막힌 걸 보고 "릴리스 빌드는 안전하다"고 결론 내리기
> 쉽기 때문입니다. 실제로 한 번 그렇게 착각했습니다. 두 경로는 다릅니다.

반대로 `PlayerPrefs`는 **내부 저장소**에 있습니다.

```
/data/data/<package>/shared_prefs/   ← 루팅 없이 읽을 수 없다
```

**두 저장소의 접근 난이도 차이가 이 문서 전체의 토대입니다.**

| | 경로 | adb만 가진 공격자 |
|---|---|---|
| 세이브 파일 | 외부 앱전용 | **읽기 O / 쓰기 O** |
| PlayerPrefs | 내부 | **읽기 X / 쓰기 X** |

## 2. 서명 — 키를 어디에 두는가

세이브를 `{payload, sig}` HMAC 봉투로 감쌉니다. 여기서 **유일하게 중요한 결정은 키의
위치**입니다.

- 앱 바이너리에 상수로 박으면 → IL2CPP 메타데이터에서 그대로 뽑힙니다. **무의미합니다.**
- `PlayerPrefs`(내부 저장소)에 두면 → adb만 가진 공격자는 읽을 수 없습니다.

그래서 키는 `PlayerPrefs`에 두고, **설치마다 무작위로 생성**합니다.
다른 기기에서 만든 파일도 자동으로 거부됩니다.

결과적으로 공격자는 세이브 파일을 **읽고 고칠 수는 있어도 유효한 서명을 만들 수 없습니다.**

### 감수하기로 한 위험

**키를 잃으면 서명된 세이브도 함께 무효가 됩니다.**
앱 데이터 삭제는 내부·외부를 함께 지우므로 세이브도 같이 사라져 문제가 없습니다. 하지만
`PlayerPrefs`만 유실되는 경우(한쪽만 복원된 백업 등)에는 정상 유저의 최고 점수가 폐기됩니다.

**"키 유실"과 "변조"는 원리상 구별할 수 없습니다.** 무결성을 얻는 대가이고, 도달 조건이
극히 좁다고 판단해 감수했습니다. 이 판단을 주석에 남겨서, 나중에 이 경로로 문의가 들어왔을
때 "버그인가?"부터 다시 시작하지 않게 했습니다.

> **그리고 이것은 치팅 방지이지 기밀 보호가 아닙니다.** 세션 내용은 여전히 평문으로
> 읽힙니다. 숨겨야 할 값이 생기면 그때는 암호화가 따로 필요합니다.

## 3. 마이그레이션이 만드는 구멍 — 다운그레이드 공격

여기가 이 설계에서 가장 까다로웠던 지점입니다.

**문제.** 업데이트로 이 코드를 처음 받는 유저는 **전원 무서명 평문 파일**을 갖고 있습니다.
세션은 못 믿으면 버리면 되지만, **`gameData`를 버리면 유저의 최고 점수가 사라집니다.**
그러니 평문을 한 번은 받아들여야 합니다.

**그런데 평문을 무제한 받아들이면 서명이 통째로 무의미해집니다.**
공격자가 "레거시처럼 보이는" 평문을 push하면 그냥 통과하기 때문입니다.

**해법.** `PlayerPrefs`에 `GameData.SignedOnce` 플래그를 둡니다.
**서명본을 한 번이라도 성공적으로 쓴 뒤에는, 평문을 마이그레이션 대상이 아니라
다운그레이드 공격으로 취급해 폐기합니다.**

이 방어가 성립하는 근거는 **비대칭성**입니다.

```
공격자가 할 수 있는 것 : 세이브 파일을 마음대로 바꾸기   (외부 저장소)
공격자가 못 하는 것    : SignedOnce 플래그를 지우기      (내부 저장소)
                        → "아직 서명한 적 없음" 상태를 위조할 수 없다
```

### 플래그를 세우는 순서까지가 설계입니다

플래그는 **서명 파일 쓰기가 성공한 직후**에 세워야 합니다.

```
[잘못된 순서] 플래그 먼저 → 쓰기 실패
  → 디스크에는 정상 유저의 평문 파일이 그대로 남아 있는데
  → 다음 실행에서 "SignedOnce인데 평문?" → 다운그레이드로 오판 → 폐기
  → 정상 유저의 데이터를 우리가 직접 지운다
```

그래서 `WriteAtomic`이 **성공 여부를 반환**하도록 만들었습니다.
반환값 하나가 이 순서 제약을 코드로 강제합니다.

## 4. 서명으로 못 막는 것 — 되감기(replay)

**서명은 "이 앱이 썼는가"만 보증하고 신선도는 보증하지 않습니다.**

```
① 누적 플레이 수가 낮았던 시절의 세이브를 adb pull 로 떠 둔다
② 나중에 push 한다  →  서명이 유효하므로 그냥 통과한다
③ AdGatePolicy 의 신규 유저 보호 조건(TotalGamesPlayed <= 3)이 다시 참이 된다
④ 전면 광고 면제. 3판마다 되밀기만 하면 영구히 반복된다
   → 서명을 붙인 목적 자체가 무력화
```

**해법.** 되감기 방어가 필요한 값 하나만 **워터마크**로 따로 남깁니다.
`GameData.GamesPlayedMark` — 지금까지 관측된 `TotalGamesPlayed`의 최댓값, 단조 증가,
`PlayerPrefs`(내부 저장소)에 둡니다.

공격자는 외부의 세이브 파일은 바꿔도 내부의 이 값은 **낮출 수 없습니다.**
되감힌 파일을 읽어도 카운터가 워터마크까지 올라가므로 보호 구간으로 돌아가지 못합니다.

### 최고 점수 되감기는 일부러 막지 않았습니다

방어를 전부 걸지 않은 것도 판단입니다.

- **서버 제출 경로가 없어 실피해가 없습니다.**
- **최고 점수는 사용자가 스스로 낮출 이유가 없습니다** → 워터마크가 곧 값 자체입니다.

실익이 없는 곳까지 막으면 코드만 늘어난다고 보고 여기서 멈췄습니다.

### 적용 순서: 클램프 → 워터마크 → 서명

```csharp
// 클램프 뒤에 워터마크를 적용한다 — 음수를 0으로 자른 값이 다시 기록값까지 올라가야 하므로.
// 그리고 클램프·워터마크까지 끝난 값을 서명한다 — 변조된 값이 서명만 얻어 살아남지 않도록.
```

세 처리의 순서가 각각 이유를 갖습니다. [수식 정규화](expression-normalization.md)와 같은
성격의 제약입니다.

## 5. 방어가 스스로 공격 목표가 되지 않게 하기

이게 가장 놓치기 쉬웠던 부분입니다.

**폐기 자체가 공격 목표를 달성시켜 버리는 경로가 있었습니다.**

```
① 공격자가 세이브 파일을 일부러 망가뜨린다
② 검증 실패 → 폐기 → 새 데이터 생성 (TotalGamesPlayed = 0)
③ AdGatePolicy 의 신규 유저 보호가 TotalGamesPlayed 를 본다
④ 전면 광고 면제  ← 파일을 부수기만 하면 되므로 서명보다 훨씬 쉽다
```

**방어를 뚫는 것보다 방어를 발동시키는 게 더 쉬운 상황**이었습니다.

해법은 복구 데이터의 초깃값을 0이 아니라 `RECOVERY_GAMES_PLAYED = 4`로 두는 것입니다.
플래그가 서 있다는 건 이 설치가 이미 저장을 해 봤다는 뜻 = 신규 유저가 아니라는 뜻이므로
보호 구간을 주지 않습니다.

값을 4로 정한 데도 이유가 있습니다. 크게 잡으면 워터마크에 영구 각인되어, 데이터를 잃은
**정상** 유저가 사실상 신규 상태인데도 광고 보호를 영영 못 받게 됩니다.
보호 구간(`GracePeriodGames = 3`)을 벗어나기만 하면 목적은 달성되므로 딱 그만큼만 넘깁니다.

> ⚠️ **여기에 결합도 부채가 있습니다.** `AdGatePolicy.GracePeriodGames`가 `private`이라
> 참조할 수 없어 상수를 손으로 맞춰 두었습니다. **튜닝값이 바뀌면 여기도 함께 올려야
> 합니다.** 지금은 주석 경고로 버티고 있고, 이런 게 정확히
> [알려진 한계 #4](known-limitations.md)(설정값 하드코딩)가 만드는 종류의 비용입니다.

같은 이유로 **세션 파일은 지울 때도 일련번호를 올립니다.** 파일만 지우면 이미 떠 둔 복사본의
번호가 그대로 유효해서, 게임오버로 세션이 정리된 뒤 복사본을 되밀면 그 판을 되살릴 수
있습니다.

## 6. 같은 사고방식의 작은 사례 — AdGatePolicy

전면 광고 빈도 제한 상태를 **어디에 저장할 것인가.**
프로젝트에는 이미 세이브 파일이 있으니 거기 넣는 게 자연스럽습니다. **넣지 않았습니다.**

이 값의 존재 이유가 "전면 광고 회피를 막는 것"이므로, **변조 문턱이 높은
쪽**(PlayerPrefs)에 둬야 합니다. 편의가 아니라 **그 데이터가 막으려는 것이 무엇인지**로
고른 결정입니다.

정책 자체는 `MonoBehaviour`가 아닌 순수 C# 클래스로, 메커니즘(`AdManager`/`Provider`)과
분리했습니다. 튜닝 파라미터는 상수 3개로 한곳에 모았습니다.

```csharp
private const int   GracePeriodGames               = 3;    // 신규 유저 보호
private const int   InterstitialEveryNGameOvers    = 3;    // 게임오버 N회마다 전면 1회
private const float MinSecondsBetweenInterstitials = 90f;  // 전면 간 최소 경과 시간
```

## 요약: 이 설계에서 반복되는 한 가지 질문

모든 결정이 같은 질문에서 나왔습니다.

> **"공격자가 실제로 무엇을 할 수 있는가?"** — 추측이 아니라 실기기로 확인하고,
> 그 능력의 경계(외부 저장소는 되고 내부 저장소는 안 된다)를 방어의 축으로 삼았습니다.

그리고 그 반대편 질문도 같이 던졌습니다.

> **"이 방어가 정상 유저에게 무엇을 할 수 있는가?"** — 키 유실 시 점수 폐기,
> 복구값 각인으로 인한 광고 보호 상실. 둘 다 감수 범위를 정하고 주석에 남겼습니다.

**남아 있는 한계**

- 서버 검증 경로가 없어 방어는 전부 클라이언트 로컬입니다. 루팅 기기는 대상 밖입니다.
- `RECOVERY_GAMES_PLAYED`와 `GracePeriodGames`가 코드로 연결되어 있지 않습니다 (위 경고 참고).
- 세이브 내용은 평문입니다. 무결성만 보증하고 기밀성은 보증하지 않습니다.
