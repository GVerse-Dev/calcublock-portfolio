## ① AutoPlayBot — 실제 코드를 오래 돌립니다

```
Assets/QA/AutoPlayBot/
├── IAutoPlayBot.cs              # 봇 실행 계약
├── IReadOnlyBoardState.cs       # 봇에는 읽기 전용 보드만 노출
├── Strategies/
│   ├── IPlacementStrategy.cs
│   └── RandomPlacementStrategy.cs
├── GameLoop/
│   ├── GameLoopRunner.cs        # 게임오버까지 무인 반복
│   └── GameLoopResult.cs
├── Metrics/
│   ├── BotMetricsCollector.cs
│   ├── MemorySnapshot.cs        # 구간별 메모리 스냅샷
│   └── BotSessionReport.cs
└── Tests/
    ├── AutoPlayBotStressTests.cs
    └── LeakSnapshotCapture.cs
```

### 결정 1 — 봇에게 쓰기 권한을 주지 않았습니다

`IReadOnlyBoardState`로 **읽기 전용 보드만 노출**합니다.

봇에게 보드를 직접 조작할 권한을 주면 테스트 작성이 훨씬 쉬워집니다. "이 상황을 만들고
싶으니 타일을 직접 세팅하자"가 가능해지기 때문입니다.

그러면 **프로덕션 코드가 실제로 도달할 수 없는 상태에서 통과한 결과**가 됩니다.
봇이 게임을 **플레이해서** 도달한 상태여야 의미가 있다고 봤습니다.

인터페이스로 막아 두면 나중에 급할 때 우회하기도 어려워집니다.

### 결정 2 — 배치 전략을 주입합니다

`IPlacementStrategy`를 인터페이스로 두어 같은 러너로 여러 전략을 비교할 수 있게 했습니다.
현재는 `RandomPlacementStrategy` 하나지만, 러너와 전략이 분리되어 있으므로 전략을 추가할 때
러너를 건드릴 일이 없습니다.

### 결정 3 — 스트레스 테스트를 테스트 러너에 편입했습니다

봇이 별도 실행 도구로 남으면 아무도 돌리지 않습니다. `AutoPlayBotStressTests`로 PlayMode
테스트에 넣어 **테스트 러너를 돌리면 함께 돌아가게** 했습니다 (3개 케이스).

`Editor-only` 어셈블리(`IGQA.AutoPlayBot.Tests.asmdef`)로 분리해서 **런타임 빌드에는
포함되지 않습니다.**

## ② 시뮬레이션 레이어 — Unity 없이 1,000판

```
Assets/Tests/EditMode/Simulation/
├── SimulationBoard.cs   # 규칙만 재현한 보드 (렌더링·입력 의존성 없음)
├── SimBlock.cs
├── SimBoardTile.cs
├── SimulationRunner.cs  # N판 동기 루프
├── IBotStrategy.cs
├── RandomStrategy.cs    # 무작위 배치 = 난이도 하한선
├── GreedyStrategy.cs    # 즉시 이득 최대화 = 숙련자 근사
├── SimulationMetrics.cs
└── MetricsExporter.cs   # CSV 내보내기
```

### 왜 봇을 재사용하지 않고 따로 만들었는가

AutoPlayBot은 **실제 게임 코드**를 돌립니다. 정확하지만 Unity 런타임 · 코루틴 · 렌더링에
묶여 있어 **1,000판을 돌릴 수 없습니다.**

밸런스 측정에 필요한 것은 정확한 연출이 아니라 **규칙의 통계적 결과**입니다. 그래서
`SimulationBoard` / `SimBlock` / `SimBoardTile`은 `MonoBehaviour`가 아닌 순수 C#이고,
`SimulationRunner`는 동기 루프입니다. **EditMode에서 수 초 내에 끝납니다.**

> 대신 대가가 있습니다. 규칙이 두 곳(프로덕션 / 시뮬레이션)에 존재하므로 **게임 규칙을
> 바꾸면 양쪽을 함께 고쳐야 합니다.** 지금은 타일 확률 생성(`TileValueGenerator`,
> `TilePhaseProfile`)과 점수 계산(`ExpressionEvaluator`)을 **프로덕션 코드에서 그대로
> 가져다 쓰는 것**으로 이 위험의 가장 큰 부분은 덮었습니다. 나머지(배치 판정·클리어 판정)는
> 여전히 중복입니다.

재현성을 위해 **전역 시드를 시뮬레이션 시작에 한 번 설정**합니다. 같은 시드면 같은
결과입니다.

### 두 전략으로 구간을 잡습니다

| 전략 | 의미 |
|---|---|
| `RandomStrategy` | 아무 유효 위치에 배치 → **난이도 하한선** |
| `GreedyStrategy` | 클리어 위치 > 가장자리 > 아무 곳, 클리어 위치가 여럿이면 수식 결과 최대 → **숙련자 근사** |

`GreedyStrategy`의 우선순위 규칙은 "숙련자가 실제로 이렇게 둔다"의 근사입니다.
정확한 최적해가 아니라 **상한의 대용치**로 쓰는 것입니다. 이 한계를 알고 쓰는 것과
모르고 쓰는 것은 다릅니다.

## 실측 결과와 거기서 배운 것

전략별 1,000판입니다. ([원본 CSV](../Assets/SimulationData/))

| | 무작위 (하한) | 탐욕 (상한 근사) |
|---|---|---|
| 평균 생존 턴 | 16.2 | **32.1** |
| **중앙값 점수** | 5 | **68,010** |
| p10 점수 | 0 | 196 |
| p90 점수 | 71,173 | 26,078,214 |
| 평균 점수 | 3,442,950 | 27,431,228 |
| 최고 점수 | 974,910,860 | 1,111,142,851 |
| 음수 점수로 끝난 판 | 3.7% | 4.1% |
| 종료 시 보드 점유율 | 0.601 | 0.607 |

### 배운 것 1 — 평균으로 밸런스를 보면 안 됩니다

**평균과 중앙값이 5자릿수 넘게 벌어집니다** (무작위: 344만 vs 5).

곱셈 연쇄가 한 번 터지면 한 판에 수억 점이 나옵니다. 그래서 평균은 상위 몇 판에 통째로
끌려갑니다. **이 게임의 밸런스는 중앙값과 분위수로 봐야 합니다.**

시뮬레이션을 돌리기 전에는 몰랐습니다. 이걸 몰랐다면 "평균 340만 점"을 기준으로 목표 구간을
잡았을 것이고, 실제 플레이어의 90%가 그 근처도 못 가는 밸런스가 나왔을 것입니다.

플레이해 보는 것만으로는 알기 어려운 종류의 사실이었습니다.

### 배운 것 2 — 실력이 점수보다 생존에 덜 반영됩니다

숙련도 차이가 **생존 턴에서는 2배**(16.2 → 32.1)인데
**중앙값 점수에서는 1만 배가 넘습니다**(5 → 68,010).

점수 곡선이 실력에 지나치게 민감하다는 뜻입니다. 오래 버티는 것보다 **큰 수식을 만드는
것**이 압도적으로 중요합니다. 게임 설계 의도와 맞는 방향이긴 하지만, 초보와 숙련자의
리더보드 격차가 극단적으로 벌어진다는 뜻이기도 합니다.

### 배운 것 3 — 음수 점수는 드뭅니다

음수로 끝난 판이 3.7% / 4.1%입니다. 음수 점수는 게임의 긴장 장치인데 **실제로는 거의
발동하지 않습니다.** 두 전략 모두 비슷한 걸 보면 실력과 무관한 구조적 특성입니다.

### 아직 하지 않은 것

**위 관측을 근거로 실제 튜닝 값을 바꾸는 단계까지는 가지 않았습니다.**
측정 도구와 기준선(baseline)을 만든 것까지가 현재 상태입니다. 여기서 멈춰 있다는 것을
적어둡니다.

## 테스트 러너에서의 위치

| 위치 | 케이스 | 성격 |
|---|---|---|
| `EditMode/LevelDesignSimulation` | 2 | 시뮬레이션 실행 + CSV 생성 |
| `PlayMode/SmokeTests` | 2 | 씬 로드 · 초기화 |
| `PlayMode/GameplayTests` | 2 | 배치 → 클리어 → 점수 반영 |
| `QA/AutoPlayBot/Tests/AutoPlayBotStressTests` | 3 | 장시간 자동 플레이 · 메모리 |

`PlayModeTestBase`가 씬 로드와 매니저 초기화 대기를 공통으로 처리합니다 — 싱글톤 초기화
순서에 의존하는 코드를 테스트하려면 이 준비가 매번 필요하기 때문입니다.

**이 준비 코드가 필요하다는 사실 자체가 [알려진 한계 #1](known-limitations.md)의
증상입니다.** 의존성이 주입되었다면 씬을 띄우지 않고도 검증할 수 있습니다.
